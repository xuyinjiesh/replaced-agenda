# 替代进程观测站 · replaced agenda

每日观察 **AI 取代人类各方面生活进程** 的静态站点流水线。覆盖数学、物理、科学发现、互联网/软件、医疗/生物、金融/法律/白领、艺术/内容创作、机器人与物理世界八个领域。

每天跑一条流水线：**采集原始资讯 → AI 初筛 → 内容填充 → 生成 `data/<日期>.json` → 渲染静态 HTML**。

首页只有一张按价值排序的当日列表。

---

## 快速开始

```bash
npm run selftest                           # 自检（不联网、不调 AI），91 项不变量
npm run pipeline                           # 跑今天的完整流水线
npm run pipeline -- --date 2026-09-28      # 指定日期
npm run audit -- --date 2026-09-28         # 跨模型独立复核当天评分
npm run render                             # 只重算指数并重新渲染 HTML
npm run probe                              # 探测数据源可达性
npm run serve                              # 本地预览 http://127.0.0.1:4180/
npm run deploy                             # 跑流水线 → 提交 site/ → 推到 GitHub Pages
```

产物：

```
data/events/2026-09-28.json    ← 当日结构化事件（约定 schema）
data/index.json                ← 领域指数时间序列
data/runs/2026-09-28.json      ← 运行报告（各阶段统计、AI 用量、校验结果）
site/index.html                ← 首页（按价值排序的当日列表）
site/day/2026-09-28.html       ← 日期页
site/domain/math.html          ← 领域页（指数曲线 + 时间线）
site/archive.html              ← 归档
site/method.html               ← 方法与口径
site/data/2026-09-28.json      ← 供前端直接 fetch 的机器可读数据
```

## 常用参数

| 参数 | 作用 |
|---|---|
| `--date YYYY-MM-DD` | 指定运行日期（默认本地今天） |
| `--refresh` | 忽略 `data/raw/` 缓存，强制重新抓取 |
| `--offline` | 只用本地缓存，绝不联网 |
| `--force-sources` | 忽略数据源健康度，强制重试所有源 |
| `--window-days N` | 收录窗口，默认 3 天（周末 arXiv 不更新时需要留缓冲） |
| `--reprocess` | 忽略 `data/seen.json`，重新评估窗口内全部条目（改评分口径后用） |
| `--max-candidates N` | 覆盖初筛候选上限（调试用） |
| `--max-enrich N` | 覆盖内容填充上限（调试用） |
| `--skip-collect` / `--skip-ai` | 跳过采集 / 跳过全部 AI 阶段（调试用） |
| `--dry-run` | 跑完整流程但不写盘、不渲染 |
| `--concurrency N` | AI 并发数，默认 3 |
| `--provider auto\|openai\|bl` | AI 传输方式（默认 `auto`：有 key 就直连 OpenAI 兼容端点，否则回退百炼 CLI） |
| `--ai-timeout N` | 单次 AI 调用超时毫秒数，默认 180000 |

## 流水线

```
config/sources.json (80 个源)
        │
        ▼
① 采集        fetch + 重试 + 同源节流 + 原文缓存 → data/raw/<日期>/
        │      单源失败不中断；连续失败的源进入冷却期
        ▼
② 规则初筛    日期窗口剔旧闻 / seen.json 剔已收录 / 正负词典剔离题 / 优先级排序
        │      → data/seen.json
        ▼
③ AI 初筛     qwen-flash 批处理：相关性、领域、初版价值/替代度/方向/证据类型
        │      规则去重（标题 2-gram Jaccard + 摘要 SimHash）先跑，省 AI 成本
        ▼
④ 灰区复核    只有规则拿不准的相似对交给 AI 判断是否同一事件
        │
        ▼
⑤ 内容填充    qwen-plus 批处理：中文摘要、关键词、原文证据片段、最终评分
        │      证据引文逐字回查原文，对不上就不写入并下调可信度
        ▼
⑥ 落盘        data/events/<日期>.json  →  全量重算指数  →  site/ 静态 HTML
```

### 为什么是这个顺序

- **规则在前、AI 在后**：一千多条原始条目里大部分是离题或重复的，先让零成本规则砍到几百条，AI 只处理有希望的。一天实测：`1285 → 320 候选 → 102 通过初筛 → 填充`。
- **候选按领域配额**：纯按优先级排序时，AI/软件类目会挤掉数学、物理这类低频但必需的领域（实测数学候选数为 0）。所以规则初筛按 `hintDomain` 分配配额（默认每领域 40 条），配额没用满再用全局优先级补足。
- **去重先于 AI 初筛**：同一篇 arXiv 论文 cross-list 到 `cs.AI` 和 `cs.LG` 会出现两次，规则去重能在调用 AI 之前就合并掉。
- **AI 复核而不是 AI 全量**：灰区复核只处理规则相似度在 0.22–0.34 之间的对，数量小、价值高。

## 事件 schema

必需字段严格遵循约定：

```json
{
  "date": "2026-09-27",
  "sector": "industry",
  "domain": "healthcare",
  "value": 0.62,
  "delta": 0.03,
  "model": "xxx",
  "source_url": "https://...",
  "evidence_quote": "原文片段",
  "evidence_type": "third_party_reproduced",
  "confidence": 0.9
}
```

- `model` 指**事件涉及的 AI 系统**（哪个模型/产品在取代人）；给这条内容打分的模型记录在 `scored_by`。
- `sector` 是频道归属（`academia` / `industry`），见下方「两个频道」。它是附加字段，不属于最初的九个必需字段。
- 每条记录还带有附加字段：`id`、`title`、`summary_zh`、`keywords`、`why_zh`、`displacement`、`direction`、`ai_systems`、`evidence_verified`、`source_name`、`also_reported_by`、`cluster_size`、`screened_by`、`scored_by`、`index_contribution`、`domain_index`。

### 三个分数

| 字段 | 含义 | 口径 |
|---|---|---|
| `value` | 推进强度 0-1 | 「AI 承担原本由人类完成的任务」这条轴上推进了多少。0.9+ = 可验证的里程碑，0.7-0.9 = 显著跃升，0.5-0.7 = 扎实进展，0.3-0.5 = 增量，<0.3 = 弱相关 |
| `displacement` | 替代程度 0-1 | 该环节的人类角色能被移除到什么程度，1 = 整环替代 |
| `confidence` | 可信度 0-1 | 从证据类型基准出发按独立性/可复现性调整 |

### 证据类型与基准可信度

| key | 名称 | 基准 | 说明 |
|---|---|---|---|
| `third_party_reproduced` | 第三方复现 | 0.92 | 独立复现或独立评测 |
| `government_filing` | 监管/政府文件 | 0.90 | 审批、政府报告、法院文书 |
| `peer_reviewed` | 同行评审 | 0.88 | 正式发表的论文 |
| `benchmark_leaderboard` | 公开榜单 | 0.80 | 可公开核验的榜单 |
| `press_release` | 官方新闻稿 | 0.70 | 选择性披露 |
| `news_report` | 媒体报道 | 0.60 | 二手报道 |
| `preprint` | 预印本 | 0.55 | arXiv 等，未经评审 |
| `vendor_claim` | 厂商自述 | 0.48 | 无独立验证 |
| `community_report` | 社区/从业者 | 0.42 | 个人观察 |
| `unknown` | 来源不明 | 0.30 | |

**证据核对闸门**：模型给出的 `evidence_quote` 会被程序逐字回查原文（容忍 12 字窗口的轻微改写，且只写入能核对上的片段）。核对不上就不写入引文，同时 `confidence × 0.6`。这是防止模型编造引文的主要手段，`method.html` 里会显示每条引文是否已核对。

## AI 传输层

流水线的 AI 调用与具体厂商解耦，`scripts/lib/providers.mjs` 提供两种传输：

| provider | 说明 |
|---|---|
| `openai` | 任意 **OpenAI 兼容端点**（DashScope compatible-mode / OpenAI / vLLM / Ollama…），直连 HTTP，无子进程开销。**默认** |
| `bl` | 阿里云百炼 CLI（子进程）。没有可用 key 时的兜底 |

凭据按优先级从**真实环境变量**或**仓库根的 `.env`** 读取，两种写法都认（YAML 风格 `key: value` 与 shell 风格 `KEY=value`）：

```bash
# 任选其一
AI_API_KEY=sk-xxx          AI_BASE_URL=https://dashscope.aliyuncs.com/compatible-mode/v1
OPENAI_API_KEY=sk-xxx      OPENAI_BASE_URL=https://api.openai.com/v1
DASHSCOPE_API_KEY=sk-xxx   base_url: https://dashscope.aliyuncs.com/compatible-mode/v1
```

切换后无需改代码：`npm run pipeline -- --provider bl`。当前使用的端点、脱敏后的 key 指纹都会打进运行日志和 `data/runs/*.json` 的 `ai` 字段，方便核对用的是哪套凭据。

> 缓存键包含 provider 名与 `extraBody`，所以换端点或换参数不会复用另一套结果，也不会互相污染。

### 混合推理模型要关掉思考模式

`deepseek-v4.1-flash` 这类混合推理模型会把 token 大量花在 `reasoning_content` 上。在这类批量 JSON 任务上实测会出现 `content` 为空、`finish_reason: length` 的情况——如果这时把 `reasoning_content` 当答案用，就会得到一段**被截断的思维过程**，解析不出条目却「看起来成功了」。

流水线对这种情况的处理：

- `providers.mjs` 只在 `finish_reason !== "length"` 时才允许回退到 `reasoning_content`，并标记 `fromReasoning`；被截断的响应**不写缓存**，避免污染后续运行。
- 需要推理模型时用 `NO_THINKING`（即 DashScope 的 `enable_thinking: false`）关掉思考模式。实测同一次调用从数千 completion tokens 降到个位数，输出干净可用。`npm run audit` 默认开启，加 `--thinking` 可关掉这个行为。
- 结构化输出不要只认一个字段名。实测同一个提示词下模型会把数组叫 `items` / `results` / `reviews`，只认 `items` 会让**整批结果静默丢失**（复核覆盖率一度只有 62%）。`audit.mjs` 现在做字段归一化，并在覆盖不全时显式告警。

## 跨模型独立复核

**评分通胀是这类系统最主要的失效模式，而同一个模型无法发现自己的偏差**——让它自查，结果会和打分时高度相关。所以另有一个复核脚本，用**不同族的模型**重新给当天事件打分：

```bash
npm run audit -- --date 2026-09-28                 # 用 .env 配置的模型复核（默认 deepseek 系）
npm run audit -- --date 2026-09-28 --sample 30     # 只抽查价值最高的 30 条
npm run audit -- --date 2026-09-28 --engine codex  # 交给 codex agent 深度复核
npm run audit -- --date 2026-09-28 --model qwen-plus
```

两个引擎：

- **`chat`（默认）**：直接调另一个模型批量复核，快、便宜，适合每天跑。
- **`codex`**：`codex exec -s read-only` 起一个只读沙箱里的智能体，自己能读日文件与运行报告，适合深入排查。注意 codex 需要可写的 `CODEX_HOME`（脚本会在 `data/.codex-home` 建一个并从真实 home 复制凭据）。

复核结果落在 `data/audits/<日期>.json`，与原评分不一致的条目会在列表里带「复核」标记。**复核不会自动改写分数**：单个复核模型的判断同样可能错，它的价值是产出一份可人工抽查的候选清单，而不是自动裁决。

### 复核本身也可能有偏差

第一次写这个脚本时，提示词里写的是「你的任务是**找出被高估的条目**，不是确认它们」。结果它稳定地报告「系统性高估 -0.12」——但那有很大一部分是**我自己提示词的偏差**，不是原评分的问题：审计员被要求只朝一个方向找，自然会朝那个方向偏。

改成中性提示词（明确要求「两个方向都保持中立，不要为了显得严格而系统性压低」）后，同样 32 条的分歧降到 **-0.06**，78% 完全一致。所以**任何只朝一个方向找错的检查都会自证其说**，报告口径也相应改成中性措辞（「复核模型整体比原评分低 X」而不是「原评分偏高 X」）。

### 实测抓到的真问题

真正被复核抓到的是**相关性误判**，不是分数尺度：AI 安全/越狱基准、纯算法改进、评测方法论文被当成了「替代人类任务」。这类问题已经回灌进初筛提示词的排除清单。

但排除清单**很容易收得过紧**：第一版写「排除纯基础设施与效率工作」，结果误杀了机器人操作、语音合成、定理证明等合法条目（通过数从 80 掉到 44）。修正后的版本把区分讲清楚——**排除的是「AI 研究 AI 自己」，保留的是「AI 去做原本人类做的事」**——通过数回到 106，同时数据中心散热之类的假阳性被正确排除。

当前残余分歧约 **-0.09**（两个模型的中位数分别是 0.55 / 0.45），且 64% 完全一致。剩下的分歧集中在**相关性尾部**而不是尺度：硬件传感组件、LLM 元测量、概念框架这类条目原分不高（0.45-0.55），对指数的实际影响有限，但严格说仍不该收录。

## 摘要缺失的定向修复

首页唯一可读的内容是中文摘要，而实测约 20% 的条目在主填充轮次会漏掉 `summary_zh`——第一版的兜底是把**英文标题**塞进摘要字段，页面上就直接显示一串英文（比留空更糟，因为它看起来像成功）。同批次里模型漏返回的条目还会被 `if (!raw) continue` **静默丢弃**。

两个问题一起修：

1. 兜底不再伪造摘要，缺失就留空并标记。
2. 主轮次之后加一轮**定向修复**：只把缺摘要/缺关键词的条目重新送一次，只问这两项。用便宜模型（`models.summarizer`），成本很低。
3. 模型漏返回的条目**保留并降可信度**，交给同一轮修复补齐，而不是丢弃。
4. 修复后仍无中文摘要的，退回标题并打上 `summaryMissing` 标记，便于在页面上识别。

自检里固化了 6 条相关不变量——包括「摘要必须落在正确的条目上」，因为修复调用是分批的、批次内下标会重复，**归位错误会静默地把 A 的摘要写到 B 上**。

## 两个频道：学术界与互联网

| 频道 | 来源 | 产出 |
|---|---|---|
| `academia` 学术界 | arXiv、期刊、独立基准机构 | 论文、预印本、基准、理论结果 |
| `internet` 互联网 | 热榜、社区、科技媒体、大公司动态、产品榜 | 当下互联网在关注什么 |

**按来源划分**，不是临时按内容判断。归属只在 AI 初筛阶段判定一次，后续环节不再改写——两个阶段各判一次会互相覆盖（实测填充阶段把互联网条目几乎全改回 `academia`，15 → 4）。

arXiv 只进学术界频道。互联网频道的实时源包括 Hacker News、Lobsters、Slashdot、V2EX、Product Hunt、GitHub Trending、Techmeme、今日头条热榜，以及 cnBeta / Solidot / 开源中国 / 少数派 / 爱范儿 / 钛媒体 / 界面 / 新浪科技，加上大公司新闻室与 Bloomberg / FT / CNBC / ZDNet / The Register / TechCrunch AI / WIRED AI。

### 互联网频道的相关性口径更宽

学术界要求能指出「哪类人类工作会变少」。互联网频道**允许间接关系**：一个好用的产品、一种新的交互方式、一次成本大幅下降，都可能具备替代潜力，即使当下还没人因此失业。

但仍然**必须与 AI 或自动化有关**。热榜里排名第一的娱乐、体育、时政新闻照样排除——实测今日头条热榜前三是「日媒惊呼中国队出了怪物级天才」这类内容，不设这条的话频道会变成社会新闻聚合。

### 「直接」与「潜力」分开算

每条记录带 `relation`：

- `direct`：能指出已被替代的具体岗位或流程 —— **计入指数**
- `indirect`：只是具备替代潜力 —— 页面照常显示，但**贡献恒为 0，不计入指数**

「这个产品有替代潜力」是**推断**而不是**观测**。把推断计入进程指数，会让「AI 取代人类」看起来比实际快——正是这个项目一开始花大力气修掉的评分膨胀。判断不了时一律按 `indirect`，宁可低估。

**`relation` 只对互联网频道有意义。** 学术界走严格口径，通过即等于直接替代，一律 `direct`。这一条是踩过坑的：一开始两个频道都让 AI 判 `relation`，结果 74 条学术条目里 60 条被标成 `indirect`，总 Δ 从 +10.5 掉到 +2.6，指数被抽空。

### 自述型来源要封顶证据类型

GitHub Trending 和 Product Hunt 的内容就是项目/产品的**自我介绍**。实测一条仓库 README 自称「我们的结果已被独立复现」，被判成 `third_party_reproduced`（上限 1.0）拿到 0.92。自述无法自证第三方复现，所以这类来源带 `evidenceCeiling: "vendor_claim"`。

这个封顶**必须在初筛和填充两处都执行**：只加在初筛会被填充阶段覆盖。抽成了 `applyEvidenceCeiling()` 供两处调用。

### 为什么用滚动窗口

频道页取**近 7 天**，而不是单日。原因是发布日 ≠ 采集日：公司博客和媒体常在发布几天后才被采到，而事件日期取发布日是对的。只看单日会让互联网频道几乎空掉（实测单日 3 条 vs 近 7 天 16 条）。带灰色日期标签的条目不是今天发布的。

### 其他实现坑

**任何「按分数排序后截断」的环节都会挤掉互联网频道。** arXiv 条目量级远大于热榜和社区，候选池、填充池两处截断都会把它整段切掉。加了 `sectorFloorShare`（默认 0.33）保底，且名额在后续裁剪中不会被砍。同理，规则初筛的 `groupBonus` 原本没有 company/labor/media/realtime 这些分组（全为 0），而 research 有 +0.4，等于反向歧视。

**热榜类源没有正文。** 今日头条热榜只给标题和热度，采集时把榜位与热度写进 `summary`，让下游知道这条是靠榜位进来的。这类条目没有可核验引文，可信度会被自动下调。

## 前端展示

纯静态：`site/` 自包含，可直接托管。**页面刻意做减法**——每页只剩两行：顶栏，和一行筛选。口径说明一律移到方法页。

### 页面只剩两行

```
AI 降临观测站 / 🌐 互联网                   互联网  学术界  归档  方法     ← 顶栏
[全部 58] [数学 1] [物理 1] [科学发现 3] [互联网/软件 32] … [筛选 /]     ← 筛选行
[事件列表]
```

**撤掉了小标题栏。** 原来它是一整行密集文字：`🌐 互联网 · 09-25–09-28 · 58 条 · Δ +1.23 · 直接 15/潜力 43 · [学术界 ⇄] · [筛选]`。删除时逐项确认了不丢信息：

| 原内容 | 去向 |
|---|---|
| 频道名 / 日期 / 领域名 | **进顶栏**（`AI 降临观测站 / 📅 2026-09-28`），不新增行 |
| 「学术界 ⇄」跳转 | 顶栏导航本来就有 |
| 统计数字（条数 / Δ / 直接·潜力） | 删除 |
| 搜索框 | 并进筛选行右侧 |

**日期页的日期、领域页的领域名只存在于小标题栏里**——直接删掉会让这些页面失去身份标识。所以先把它挪进顶栏再删。全站原本一个 `<h1>` 都没有，这次也没有新增标题行。

**chip 上显示的是条数，不是增量。** 增量换成条数，因为 9 个 chip 里 6 个增量是 `±0.000`，扫过去全是噪声，而且要先理解指数口径才有意义；条数一眼就知道这个领域有多少内容。指数仍然算、仍然进 `index.json`，只是不摆在导航条上。

计数是**筛选计数**，会随检索变化：各领域之和恒等于「全部」，也恒等于列表行数（实测 58 = 58 = 58）。等宽 + `tabular-nums`，让 `1` 和 `32` 的数字位对齐。

|---|---|
| `index.html` | 互联网频道（默认落地页） |
| `academia.html` | 学术界频道 |

| `domain/<领域>.html` | 单领域跨日记录 |
| `method.html` | 口径、局限与复现说明 |

### 火焰图标暂时留空

它本该表示「高讨论度」。既然算不出来（理由见下），就先空着——**曾经拿它标「推进强度 ≥0.70」，那是模型的打分，和「多少人在讨论」是两回事**，读者看到火苗会以为那是社区热度。宁可空着，也不要一个名不副实的图标。推进强度由数值列的颜色表达，信息没有丢。

### 做不到的标签：高讨论度

想给「很多人正在讨论」的条目一个标记，但**当前没有任何数据能算**，查证过程如下：

1. 有互动量接口的源只有两个（HN Algolia 的 `points`/`num_comments`、今日头条热榜的 `HotValue`），
2. 而这两个源**产出的事件数是 0**——它们的内容在相关性初筛里全被刷掉了，
3. 真正产出事件的社区源（Reddit、Slashdot、V2EX、Solidot）全是 **RSS**，RSS 里天然没有分数和评论数，
4. Reddit 的 JSON 接口在本机**不可达**（`curl` 返回 HTTP 000），换不了。

所以「高讨论度」暂时不做。**尤其不能拿推进强度冒充它**——那是模型的打分，和「多少人看过」完全是两回事。硬凑一个出来会让读者以为是社区热度。

如果确实要做，可行的路径是加一步「HN Algolia 反查」：拿每条事件的标题去 HN 搜一次，命中就记下分数和评论数。但**只有上过 Hacker News 的条目才有数**，其余为空——而「没有数据」会被读成「没人讨论」，这个歧义必须先在界面上讲清楚，否则不如不做。

### 卡片是表格列，标题在第一列

```
标题（最多两行）                                   领域            强度   可信度      备注
NewsGuard 审计显示主流 AI 聊天机器人频繁引用…      互联网 / 软件   0.92   高可信 .92   🔥
《自然》报道 Anthropic AI 生物实验室发现病毒中…    科学发现        0.88   高可信 .88   09-25 🔥 潜力
```

用 CSS Grid 而不是 `<table>`：每行还要能展开摘要，`<details>/<summary>` 塞不进表格语义里。列宽定死，行与行之间纵向对齐。

**页面宽度 1240px**（`--page-w`）。这个数字是算出来的，不是拍的：列宽合计 424px + 列间距 60px + 内边距 44px，剩 712px 给标题列——而最长的中文标题是 46.9 字宽 ≈ 680px。**120 条标题里 0 条会被截断。**

列宽用 **px 而不是 em**。`em` 在 `grid-template-columns` 里是相对网格容器的字号算的，而各列自己的字号不同（领域 12px、数值 14.5px、可信度 11px），用 em 会让「领域」列实际只有 108px，**「📊 金融 / 法律 / 白领」一直被静默截断**。

**标题单行。** 中途试过放宽到两行（940px 宽时单行会切掉 24% 的标题），但加宽到 1240px 后单行就够了，省略号只是窄屏兜底。860px 以下标题换到独立一行，其余列继续对齐。

**去掉了每行的五个火苗。** 原来每行都画推进强度，扫起来满屏都是，没有区分度。现在只有「显著跃升」及以上（`value ≥ 0.70`）在**备注栏**给一个 🔥，全站 120 条里只有 3 条。

### 备注栏的标签

备注栏（最后一列）放：日期、标签、复核分歧。

**标签只标「例外」，不标「常态」。** 一个标签如果命中 80% 以上的条目就没有区分度——「一手信息」在学术界命中 99%（77 条里 76 条是作者自己的预印本），标了等于没标，所以不设。同理，某个标签如果能从别处直接读到（「高可信度」和左边的可信度列说的是同一件事），也不设。

留下的四种，每种都能从已有字段直接判定，不需要额外采集：

| 标签 | 判据 | 条数 | 含义 |
|---|---|---|---|
| **同行评议** / **已复现** / **官方文件** | `evidence_type` | 3 | 独立于当事人的验证，证据最硬 |
| **厂商自述** | `evidence_type = vendor_claim` | 0 ⚠️ | 厂商自己的说法，未经独立验证 |
| **小道消息** | `community_report` 且可信度 < 0.60 | 13 | 社区转述，未经核实 |
| **首次** | 标题或摘要原文含「首次／首个／第一次」 | 7 | 从原文认出来的，不是模型打分推的 |
| **潜力** | `relation = indirect` | 21 | 只是推断，不是观测，不参与指数 |

（132 条事件。实测每行最多 2 个标签：0 个 96 行、1 个 28 行、2 个 8 行。）

前三行是同一个问题的三段（证据离当事人有多远），所以互斥；「首次」和「潜力」是另外两个维度，可以叠加。

**「厂商自述」当前命中 0 条**，不是坏掉了：`prompts.mjs` 里明确写了「发布了模型 X 但没有部署场景与规模数字的，标 relation=indirect，**不必按 vendor_claim 压分**」。也就是说评分设计本身在回避这个类型，模型于是几乎不选它。标签留着等语料里真出现厂商能力宣称时再用——但如果你希望它经常生效，得先改提示词口径。

**「首次」是事实标签，不是分量标签。** 它说的是「原文声称首次」，7 条里有 6 条是「首个……基准」这类学术首发，份量远不如「历史突破」四个字给人的预期。原来想叫「历史突破」，但那是把模型打分包装成历史判断，站点的口径不允许——所以改成只认原文里的首次字样。

**没有做「高讨论度」。** 详见下面「做不到的标签」。

**日期在多天列表里每行都显示。** 最初是「等于窗口最后一天就不显示」，想让「没有标记 = 今天发布的」——但这靠猜，读者分不清「因为是今天所以不显示」和「日期丢了」，**空白看起来就像 bug**。现在改为：

| 页面 | 日期 |
|---|---|
| 频道页 / 领域页（多天混合） | 每行都显示 |
| 日期页（整页同一天） | 行内不显示，表头已有 |
| 归档时间轴（按天分组） | 行内不显示，分组标题已有 |

### 折叠用原生 `<details>`，不依赖 JS

折叠一度挂在 `<html class="has-js">` 上，这个类由 `<head>` 里的内联脚本添加。**这个设计有个致命处：脚本一旦没跑（CSP、缓存、禁用 JS），类名就不存在，摘要会直接铺出来**——而且 HTML 看起来完全正常，检查标签结构发现不了。

现在用原生 `<details>`：不带 `open` 就是收起的，和 JS 无关。搜索自动展开、点标题不误触这些增强由 `app.js` 做，全部失效也不影响默认收起。

### 摘要里公司和概念要标出来

填充阶段额外产出 `companies`（公司/机构名）和 `concepts`（产品名、基准名、技术名词），渲染时在标题和摘要里用两种颜色标出：

- <span style="color:#1f6feb">**公司名**</span>（蓝）—— 谁在做这件事
- <span style="color:#8250df">**关键概念**</span>（紫）—— 用什么做的

**实现上先按原文切分、再逐段转义，而不是先转义再替换。** 后者会把 `&lt;` 里的字母也当成可匹配文本，而且模型给的词一旦含 `<` `>` 就会注入。切分用「最长优先」避免短词吃掉长词，纯 ASCII 词加 `\b` 边界——否则 `AI` 会在 `said` 里命中。

**推进强度用两个维度同时表达**，避免读者去猜：

- **火焰数量**（0-5，半档精度）＝ 绝对强度，跨天可比。实测 value 高度集中在 0.45-0.65（硬闸门压出来的），用五档会让几乎所有卡片同色，所以做成半档以保留分辨力。
- **热色**＝ 0.30-0.90 区间上连续插值（石板灰 → 琥珀 → 橙 → 红 → 深红），配合卡片左侧色条。暗色模式朝白提亮以保住对比度。

### 可信度只强调两端

证据类型先验天然分三带：社区转述/厂商自述 0.4-0.5、预印本/新闻 0.55-0.7、同行评议/第三方复现/政府文件 0.8-0.92。

中间那档占绝大多数（实测 120 条里 94 条），**全部标记等于没标记**。所以只把两端挑出来：

- `≥ 0.75` → **▲ 高可信**（绿色）
- `< 0.50` → **▼ 低可信**（琥珀色）
- 中间 → 素色「可信 0.55」，不抢注意力

### 归档页是时间轴，不是流水账

不做「每天一堆条目」的列表，只挑**每天价值最高的 5 条**，按日期串成时间轴。要回答的是「这段时间里最要紧的事是什么」，而不是「每天都发生了什么」。完整记录仍在日期页。

### CSS「写对了但没命中」踩的坑

这类 bug 已经犯了四次，共同点是**渲染出来的 HTML 完全正常，CSS 语法也没错，只有肉眼看才发现**——而肉眼看正是最不可靠的一环。

| 症状 | 原因 | 修法 |
|---|---|---|
| 标题栏变成一条极窄的空条 | 新标题栏 `class="bar"` 撞上旧领域网格的进度条 `.bar { height: 4px; overflow: hidden }` | 改名 `.navline`，并删掉死掉的进度条样式 |
| 归档页标题一片刺眼黄底 | 高亮写成 `.title .hl-ent` / `.summary .hl-ent`，而时间轴的高亮落在 `<div class="tl-head">` 里，选择器没命中，`<mark>` 退回浏览器默认黄底 | 去掉祖先限定，只留 `.hl-ent` / `.hl-con` |
| 归档页一片扎眼黄数字 | `.tl-val` 跟着热色走，而热色刻度 0.42-0.55 那段正好是琥珀黄 | 数字改中性色，强度信息交给左侧圆点 |
| 暗色模式与移动端的可信度规则失效 | 卡片首行从 `.evtop` 改名 `.row`，但 `@media` 里的覆写还写着 `.evtop` | 同步改名；并加测试自动拦截这类残留 |
| 摘要又铺出来了 | 折叠挂在 `<html class="has-js">` 上，而那个类靠内联脚本添加 | 改用原生 `<details>`，去掉这个开关 |
| 表格列布局没生效，还是 flex | 新的 grid 规则写在文件前面，旧的 flex 规则留在后面；同选择器、同特异性，**后面的赢** | 删掉旧块；并加测试拦截顶层重复选择器 |
| 全站页脚的上边距变成 22px | 领域页的注释复用了 `.foot`，把页脚的 `margin-top: 60px` 覆盖掉 | 注释改用独立类名 `.pagenote` |
| 「厂商自述」标在了一条独立复现的成果上 | 证据封顶把 `evidence_type` **改写**成了 `vendor_claim`，而不是只压分值 | 封顶改为只算分（`evidenceCeilingCap`），保留模型的原判类型 |
| 删掉小标题栏后日期页没有日期了 | 日期/领域名只存在于那一行里 | 先挪进顶栏，再删整行 |

**教训有两条：**

1. **删除 UI 模块时要连它的 CSS 一起删**，否则残留的类名会劫持后来的同名元素。
2. **给元素类名写样式时不要加祖先限定**，除非那个限定是刻意的。`.hl-ent` 这种只由 `highlightTerms()` 产出的类名本身已经足够具体，加 `.title` 前缀只是给未来的自己埋雷。

**光靠检查 HTML 结构发现不了这类问题**，所以 `npm test` 里加了两组反向检查：

1. 把渲染产物里真实出现的 `<mark>` 祖先类名抓出来，回到 CSS 里查有没有规则命中。
2. **把 CSS 里出现的每个类名拿去渲染产物里找**，找不到就是残留（`@media` 里的覆写最容易漏）。这条测试刚加上就抓出了 `.delta`。
3. **查顶层有没有同选择器的重复定义**。同选择器写两次，后面的会静默覆盖前面的——grid 被 flex 覆盖就是这么发生的，页面上完全看不出原因。加上后立刻抓出 `.foot` 和 `:root` 两处真冲突。

另外还守了 CSS 花括号平衡——曾经有个多余的 `}`（175 开 / 176 闭），是脚本替换 CSS 区块时算错结束位置留下的。

### 其他标记

| 元素 | 含义 |
|---|---|
| `*` | 分值已被硬闸门截断（悬停显示是证据类型不足还是缺少依据） |

## 指数模型与 delta

每个领域一个 0-100 的进程指数，用饱和曲线把累计贡献映射成指数：

```
贡献 c = direction × value × confidence     (advance = +1, setback = -1, neutral = 0)
指数 I = 100 × (1 - e^(-累计贡献 / K))
       K = dailyBaseline × horizonDays       (horizonDays 默认 90，见 config/scoring.json)

单条事件的 delta = I(累计 + c) - I(累计)
```

`dailyBaseline` 是「该领域的日均贡献基线」，`K` 由它推导。这样定义的好处：在正常节奏下**每个领域的指数都约在 90 天后达到 63%**，日环比量级统一（正常一天合计约 +1 到 +3），单日热点不会把不同领域拉出量级差异。

由此得到两条可核验的性质：

1. **同一领域同一天所有事件的 `delta` 之和，恒等于该领域当日指数变化量。** 可加、可核验。
2. 流水线每次运行都会独立复算一遍公式并断言这个恒等式（`verifyIndex`），不一致就以退出码 2 报错。

`direction` 为 `setback` 的事件（监管禁止、翻车、论文被撤）贡献负值，因此 delta 可以为负。

## 硬闸门：证据不足就不许给高分

**分数通胀是这类系统的头号故障模式。** 实测第一版跑出来的 102 条里，value 中位数是 0.70、75 条 ≥0.70——模型把普通预印本全打成了「显著跃升」。光靠提示词约束不住，所以有两道**代码强制**的闸门，在 AI 打分之后套用：

1. **依据闸门**：`value ≥ 0.65` 时必须填 `evidence_basis`（具体基准名与数字，如 `SWE-bench Verified 71.2%`，或真实部署规模）。写不出具体依据的，直接压到 ≤ `0.60`。
2. **证据类型闸门**：证据类型决定 value 上限，没有对应等级的证据就不允许给出对应等级的推进强度。

| 证据类型 | value 上限 | | 证据类型 | value 上限 |
|---|---|---|---|---|
| `third_party_reproduced` / `government_filing` | 1.00 | | `press_release` | 0.75 |
| `peer_reviewed` | 0.90 | | `news_report` | 0.70 |
| `benchmark_leaderboard` | 0.85 | | `preprint` | 0.65 |
| `vendor_claim` | 0.60 | | `community_report` | 0.45 |

被闸门截断的记录在列表里带 `*` 标记，字段里带 `value_capped`。

此外流水线每天做**评分分布自检**：value 中位数应落在 0.30–0.55、高价值（≥0.7）占比应 ≤15%、confidence 中位数应落在 0.40–0.75。越界时运行日志给出「评分分布告警」，`site/method.html` 会展示最新一天的分布对照表。

## 数据源

在 `config/sources.json` 里注册了 126 个源，覆盖 AI 实验室博客、arXiv 各分类、期刊、媒体、社区、基准评测、政策与工程博客，**实时热点源**（Hacker News / Lobsters / Slashdot / V2EX / Product Hunt / GitHub Trending / Techmeme / 今日头条热榜）、**大公司新闻室**（Apple / Microsoft / Salesforce / Samsung / AWS）、**行业媒体**（Bloomberg / FT / CNBC / ZDNet / The Register / TechCrunch AI / WIRED AI / Google News / The Information）、**中文来源**（cnBeta / Solidot / 开源中国 / 少数派 / 爱范儿 / 钛媒体 / 界面 / 新浪科技 / 量子位 / InfoQ 中文）和**劳动力市场信号**（Layoffs.fyi / Indeed Hiring Lab）。

每个源带三个提示字段：`hintDomain`（领域兜底）、`sector`（频道先验）、`evidenceCeiling`（自述型来源的证据类型上限）。后两者最终仍由 AI 按内容判定，但先验决定了哪些源进哪个频道。

流水线自动处理可达性：

- 带超时、指数退避重试、**同源串行 + 最小间隔**（arXiv 对突发并发很敏感，这是最容易踩的坑）
- 原始响应缓存到 `data/raw/<日期>/`，重跑不重复抓
- 健康度记录在 `data/source-health.json`，连续失败 3 次的源进入 7 天冷却，`--force-sources` 可强制重试
- 单源失败绝不影响整体流程

本环境的出网走代理白名单（所有域名解析到 `198.18.0.0/15` 的 fake-IP），可达集合会随时间变化：实测同一份配置，不同时刻可用源数是 **55 / 70 / 72**，一次采集 1000–1600 条原始条目。所以别把可达性写死在代码里——配置照旧全量注册，由流水线的健康度机制决定当天用哪些。

用 `npm run probe` 可以随时看当前可达情况：

```

OK   200 feed      571ms  MIT Technology Review  items=10

...
可用 70/80，共 5631 条原始条目

```

新增源只需往 `config/sources.json` 的 `sources` 数组里加一条：

```json
{ "id": "my-feed", "name": "My Feed", "group": "media", "kind": "rss",
  "url": "https://example.com/feed.xml", "hintDomain": "healthcare",
  "maxItems": 25, "enabled": true }
```

源目录按领域铺开，其中数学领域专门挂了 `cs.LO`（自动定理证明）、`cs.SC`（符号计算）、`cs.MS`、`math.NA` —— 纯数学分类（`math.AG`/`math.NT`/`math.CO`）一天里几乎不会有「AI 替代数学家」的证据，只靠它们会让数学领域长期空着。

`group` 影响去重时的主记录优先级（`third_party` > `journal` > `research` > `benchmark` > `ai-lab` > `media` > `community`）。

## 成本与可复现性

所有 AI 调用按 `sha256(model + temperature + system + user)` 缓存在 `data/cache/ai/`：

- 同一天重跑**不会重复计费**，结果完全一致
- 想强制重新判定某批内容，删掉对应的缓存文件，或用 `--refresh`
- 每次运行的 token 用量与缓存命中数记录在 `data/runs/<日期>.json` 的 `ai` 字段

模型档位在 `config/scoring.json` 的 `models` 里：初筛用 `qwen-flash`（便宜、量大），填充用 `qwen-plus`（质量优先）。

## 部署（GitHub Pages）

站点是**零构建**的：`site/` 目录整个就是可托管的成品，不需要 Node、不需要服务器端运行时。

```bash
npm run deploy          # 跑流水线 → git add -A → commit → push
```

### 一次性设置

1. 在 GitHub 建一个**空仓库**（不要勾 README，否则首次 push 会冲突），然后：

   ```bash
   git remote add origin git@github.com:<用户名>/<仓库名>.git
   git push -u origin main
   ```

2. 仓库 **Settings → Pages → Build and deployment → Source** 选 **GitHub Actions**。

之后每次 `npm run deploy` 都会自动上线，地址形如 `https://<用户名>.github.io/<仓库名>/`。

### 为什么用 Actions 而不是「从分支根目录发布」

Pages 的「Deploy from a branch」只能发布**分支根目录**或 **`/docs`**。这个仓库的根目录是代码（`scripts/`、`config/`、`README.md`），站点在 `site/` 子目录里，所以从根目录发布只会得到 `…/site/` 这种带一级前缀的地址，而且会把源码目录一并公开。

`.github/workflows/pages.yml` 改为只把 `site/` 打包上传，于是：

- 地址是干净的仓库根路径，没有 `/site/` 后缀
- 源码目录不进入 Pages 站点（代码仍然在仓库里，只是不作为网页发布）
- CI 只做上传，**不抓源、不调 AI、不需要任何密钥**——流水线始终在你本机跑

站点内所有链接都是相对路径（`../assets/style.css`、`day/2026-09-28.html`），所以仓库改什么名字都不用动代码。

### 提交 site/ 的取舍

`.gitignore` 里 `site/` 已被放开，产物会进版本库。约 1.5 MB/次、每天一次提交，一年约 550 MB。换来两个好处：

- 线上内容可追溯——能 `git log -p site/data/index.json` 看指数哪天跳的
- 部署不依赖 CI 能联网（这一点很关键：CI runner 的出口 IP 经常被 arXiv、Bloomberg、今日头条挡掉，跑出来的数据会比本机差）

### 密钥安全

`npm run deploy` 在提交前会显式断言 `.env` 仍被 `.gitignore` 忽略，一旦发现它变成可跟踪状态就**中止发布**并报错——因为放开 `site/` 等于动了同一份 ignore 规则，这层校验不能省。

`.env` 里的 key 任何时候都不该进仓库。已检查过 `site/` 的每个文件（HTML/CSS/JS/JSON），不含任何凭据；`site/data/seen.json` 只有哈希 id 与日期，没有标题。

### 自定义域名

在 `site/` 下放一个 `CNAME` 文件，内容写域名（一行，无协议），然后在仓库 Settings → Pages 填同一个域名并配置 DNS。注意 `CNAME` 会被下一次渲染保留（渲染只覆盖页面与 `assets/`），不会被清掉。

## 已知局限

- **来源覆盖取决于网络可达性**。受限环境下媒体与期刊站点大量不可达，记录会偏向预印本与官方博客，对「真实岗位替代」类事件不敏感。
- **评分是模型判断，不是测量**。同一事件换一个模型可能差 0.1–0.2。档位表与证据类型权重是为了压低漂移，但不能消除。
- **预印本不等于事实**。大量记录的 `evidence_type` 是 `preprint`，可信度基准仅 0.55。
- **指数不可跨领域比较**。各领域 K 与事件密度不同，只适合看单领域随时间的走向。
- **候选上限**：初筛候选默认上限 320 条、填充上限 120 条，超出部分留待提高配置后处理（`data/runs/*.json` 会记录实际丢弃量）。
